## Context

Currently the backend returns complete LLM responses after full generation completes, causing perceived latency delays. The assistant chat endpoint blocks until the entire response is generated before sending to the client. The frontend waits for the full response before displaying anything.

## Goals / Non-Goals

**Goals:**
- Set stream argument from Llama class to True in order to receive a Generator object for iterating chunks on it
- Implement SSE streaming for LLM chat endpoint using FastAPI `StreamingResponse`
- Update frontend to consume SSE stream and render tokens incrementally as they arrive
- Maintain backward compatibility with non-streaming fallback if needed
- Full LLM response should be stored on backend database (you can use fastapi.BackgroundTasks.add_task function after iterating all data chunks to store the full chunk list on database)
- Store full LLM response on JavaScript localStorage object  

**Non-Goals:**
- Do not modify database schemas or data models
- Do not change the RAG retrieval logic (only response streaming)
- Do not implement WebSocket (SSE is sufficient for this use case)

## Decisions

1. **SSE over WebSocket**: Use Server-Sent Events for uni-directional streaming (server → client). SSE is simpler, works over HTTP/1.1, and has built-in reconnection support. WebSocket is overkill for response-only streaming.

2. **StreamingResponse with async generator**: Use FastAPI's `StreamingResponse` with an async generator that yields chunks as they're generated by the LLM. This avoids buffering the entire response.

3. **SSE event format**: Use standard SSE format with `data: <chunk>\n\n` for content chunks and `data: [DONE]\n\n` to signal completion.

4. **Frontend EventSource API**: Use JavaScript's native `EventSource` (or custom fetch with ReadableStream) for consuming SSE. `EventSource` has limitations (no custom headers), so a fetch with `ReadableStream` approach may be better for authentication.

5. **Incremental rendering**: Append each received chunk to the displayed response in real-time, avoiding full re-renders.

## Risks / Trade-offs

- **[Risk] LLM library compatibility**: Some LLM providers may not support streaming natively → *Mitigation*: Wrap LLM calls in async generator, buffer and flush chunks
- **[Risk] Network interruption**: SSE connection may drop → *Mitigation*: Use automatic reconnection via EventSource or manual fetch retry logic
- **[Risk] Frontend performance**: Frequent DOM updates per chunk → *Mitigation*:Batch updates or use virtualized text component
